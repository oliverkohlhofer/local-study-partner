# Study Expert – A Local RAG Chatbot for PDF Study Materials

A small, fully local **Retrieval-Augmented Generation (RAG)** application. It indexes your PDF study scripts into a vector database and lets you ask questions about them in a command-line chat or a Streamlit browser interface. Answers are generated by a local LLM running in [Ollama](https://ollama.com) with a prompt that instructs the model to use only retrieved document excerpts. Answers can still contain mistakes.

Everything runs on your own machine: no API keys, no cloud services, no data leaving your computer.

**Usage:**
If you want to have precise answers directly from a specific document, without additional hallucination from outside, or if you have sensitive documents that should be not uploaded to online LLMs.

## Features

- **100 % local** – embeddings and answer generation both run through Ollama.
- **PDF ingestion** – every `*.pdf` in the `materials/` folder is loaded page by page and split into overlapping chunks.
- **Persistent vector store** – embeddings are stored in [Chroma](https://www.trychroma.com/) on disk, so indexing only happens once.
- **Grounded answers** – the prompt instructs the model to answer *only* from the retrieved excerpts, and to say so if the answer is not in the material.
- **Source references** - excerpts include PDF names, physical page numbers, chapters, and sections. Answers are prompted to cite `[Source N]`; the CLI prints source details and a grouped summary, and the GUI displays the grouped summary.
- **Browser interface** - Streamlit renders Markdown and LaTeX answers alongside the question.
- **Simple CLI chat loop** – type a question, get an answer; write ``exit`` or ``quit`` to leave.

## How It Works

The project has two phases: **indexing** (once) and **question answering** (every query).

```
INDEXING (first run only)
─────────────────────────
 materials/*.pdf
       │  PyPDFLoader (one Document per page)
       ▼
 RecursiveCharacterTextSplitter
 (chunk_size=2500, chunk_overlap=250)
       │
       ▼
 OllamaEmbeddings (mxbai-embed-large)
       │
       ▼
 Chroma vector store  ──►  ./chroma_chapters/  (persisted on disk)


QUESTION ANSWERING (every query)
────────────────────────────────
 User question
       │
       ├──► Retriever (Chroma, top k=3 similar chunks) ──► {context}
       │
       └──► {question}
                 │
                 ▼
        ChatPromptTemplate  (context + question + strict instructions)
                 │
                 ▼
        OllamaLLM (llama3.2:3b)
                 │
                 ▼
        StrOutputParser  ──►  Answer + retrieved sources (CLI or GUI)
```

The pipeline is wired together with the **LangChain Expression Language (LCEL)** in `main.py`:

`build_chain()` returns `(chain, text_extention)`. The caller appends the selected
prompt's `text-extention` to the question before invoking the chain. Retrieval
returns three chunks; `format_documents()` labels them `[Source N]` and includes
their metadata in the model context. The chain returns a dictionary containing
`question`, `sources` (the retrieved documents), and `answer`.

## Project Structure

```text
.
|-- main.py                 # Shared RAG chain, source formatting, CLI
|-- interface_handler.py    # Streamlit browser interface
|-- settings.json           # Answer model and prompt profiles
|-- vertorize.py             # PDF ingestion, embeddings, retriever
|-- pdf_metadata.py          # Chapter/section metadata from PDF bookmarks
|-- start_interface.bat      # Windows launcher (expects venv/)
|-- materials/              # Place PDF study scripts here
|-- chroma_chapters/        # Persistent Chroma database
```

| File | Responsibility |
|---|---|
| `vertorize.py` | Loads PDFs, splits them into chunks, creates embeddings, builds/opens the Chroma store, and exposes a `retriever` object. |
| `main.py` | Loads settings, builds the RAG chain, formats sources, and runs the CLI. |
| `settings.json` | Defines the answer model and prompt profiles. |
| `pdf_metadata.py` | Maps physical PDF pages to numbered chapter/section bookmarks. |
| `interface_handler.py` | Streamlit question/answer interface with Markdown and LaTeX rendering. |
| `start_interface.bat` | Windows launcher using the project virtual environment. |

> **Note:** `main.py` does `from vertorize import retriever`. Importing that module runs the ingestion logic at import time, so the database is created automatically the first time you start the app.

## Setting Up Ollama Locally

[Ollama](https://ollama.com) is a lightweight runtime that downloads and serves open-source LLMs and embedding models on your machine through a local HTTP API (default: `http://localhost:11434`).

### System Requirements for Running Ollama Locally

Local LLMs are mostly limited by **memory**. The model weights must fit into RAM (CPU mode) or VRAM (GPU mode), plus some extra for the context window and runtime overhead. Check these requirements *before* installing.

#### Operating system

| OS | Requirement |
|---|---|
| Linux | A recent 64-bit distribution (x86_64 or ARM64), e.g. Ubuntu 22.04/24.04, Debian, Fedora |
| macOS | A recent macOS version; Apple Silicon (M1 or newer) is strongly recommended. Intel Macs work but run on CPU only and are slow |
| Windows | Windows 10 (22H2) or newer, 64-bit; Windows 11 recommended |

Exact minimum versions change between Ollama releases, so check <https://ollama.com/download> for the current list.

#### Memory (RAM / VRAM)

Rule of thumb from the Ollama project: about **8 GB of RAM for 7B-parameter models, 16 GB for 13B models and 32 GB for 33B models**. Smaller models such as the 3B model used here need less.

| Model | Download size (approx.) | Role in this project | Recommended free memory |
|---|---|---|---|
| `llama3.2:3b` | ~2 GB | Answer generation (default) | 6 GB or more |
| `mxbai-embed-large` | ~0.7 GB | Embeddings (indexing and every query) | ~1 GB on top |
| `llama3.1:8b` | ~5 GB | Optional, better answers | 10 GB or more |
| `qwen2.5:7b` | ~5 GB | Optional, better for German | 10 GB or more |

For this project the **practical minimum is 8 GB of total system RAM**, with browser and other heavy programs closed. **16 GB is recommended**, because the operating system, Python, Chroma and both Ollama models all need memory at the same time.

On a machine with a dedicated GPU, the model is loaded into VRAM instead. A 3B model fits comfortably into 4 GB of VRAM; 7B/8B models typically need 6–8 GB. If the model does not fit completely, Ollama splits it between GPU and CPU, which works but is considerably slower.

On **Apple Silicon**, CPU and GPU share one pool of "unified memory", so the total RAM of the Mac is what counts.

#### Processor and GPU

| Setup | What to expect |
|---|---|
| **CPU only** | Works with any modern 64-bit CPU. A CPU with AVX2 support and 4+ cores is recommended. Expect roughly a few to ~15 tokens per second for a 3B model, depending on the CPU. Fine for study use, but long answers take a while |
| **NVIDIA GPU** | Supported with a recent driver and a reasonably modern card (compute capability 5.0 or higher). Fastest option on Windows and Linux |
| **AMD GPU** | Supported on selected Radeon cards via ROCm (Linux and Windows); the supported list is limited, so check the Ollama documentation first |
| **Apple Silicon** | GPU acceleration through Metal works out of the box; very good speed for 3B–8B models |

Check whether a loaded model runs on the GPU or the CPU with:

```bash
ollama ps
```

The `PROCESSOR` column shows e.g. `100% GPU`, `100% CPU` or a split such as `30%/70% CPU/GPU`.

#### Disk space

- About **3 GB** for the two models used in this project (`llama3.2:3b` and `mxbai-embed-large`).
- Add **5 GB or more** per additional 7B/8B model you want to try.
- The Chroma database is small compared to the models: it grows with the number of chunks (each chunk stores its text plus an embedding vector with 1024 values). A few hundred pages of PDFs usually take only tens of MB.
- An SSD is recommended; model loading from a slow hard disk can take noticeably longer.

#### The context window and your prompt size

Each question sends the **3 retrieved chunks** (up to 2,500 characters each) plus the instructions and the question to the model. That is up to **7,500 characters of excerpts**, plus source metadata; token counts depend on the text and language. Ollama's default context window is limited (often 4,096 tokens, older versions only 2,048), so long prompts can get **silently truncated**, and the model may miss part of the retrieved context.

If answers seem to ignore information you know is in the scripts, raise the context size in `main.py`:

```python
model = OllamaLLM(model=settings["model"], num_ctx=8192)
```

A larger context window uses more memory (the key-value cache grows with it), so plan for roughly 1–2 GB of additional RAM/VRAM at 8,192 tokens for a 3B model. Alternatively, reduce `chunk_size` or `k` in `vertorize.py`.

#### Memory behaviour at runtime

- Ollama loads a model into memory on first use and keeps it loaded for about **5 minutes** after the last request, then unloads it. The first question after a pause is therefore slower. You can change this with the `OLLAMA_KEEP_ALIVE` environment variable (e.g. `OLLAMA_KEEP_ALIVE=30m`).
- The embedding model and the chat model can be loaded at the same time; this is why the memory recommendations above add up both models.
- Indexing a large set of PDFs is the heaviest step: every chunk is sent to the embedding model. It is CPU/GPU intensive and can take several minutes, but it only happens once.

#### Quick check: is my computer suitable?

| Your machine | Verdict for this project |
|---|---|
| 4 GB RAM, no GPU | Too little. The 3B model will swap and be extremely slow or fail |
| 8 GB RAM, CPU only | Works with `llama3.2:3b`; slow but usable. Keep other programs closed |
| 16 GB RAM, CPU only | Comfortable for the 3B model; 7B/8B models run but slowly |
| 16 GB RAM, Apple Silicon | Good: 3B–8B models run smoothly |
| NVIDIA GPU with 6–8 GB VRAM | Very good: 3B–8B models run fast |
| 32 GB RAM or 12 GB+ VRAM | Room for larger models (13B and above) |

### 1. Install Ollama

**Linux**

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

The installer normally registers Ollama as a `systemd` service and starts it automatically.

**macOS**

Download the installer from <https://ollama.com/download>, open it, and move Ollama to your Applications folder. Launching the app starts the background server. Alternatively, with Homebrew:

```bash
brew install ollama
```

**Windows**

Download and run the installer from <https://ollama.com/download>. Ollama runs in the background and appears in the system tray.

### 2. Verify the installation

```bash
ollama --version
```

Check that the server is reachable:

```bash
curl http://localhost:11434
# Expected output: "Ollama is running"
```

If the server is not running, start it manually in a separate terminal:

```bash
ollama serve
```

(On Linux with systemd you can also use `sudo systemctl start ollama` and `sudo systemctl status ollama`.)

### 3. Download the required models

This project needs **two** models – one for answering and one for embeddings:

```bash
# Chat / answer-generation model (about 2 GB)
ollama pull llama3.2:3b

# Embedding model used to vectorize documents and queries (about 670 MB)
ollama pull mxbai-embed-large
```

Confirm both are available:

```bash
ollama list
```

You should see `llama3.2:3b` and `mxbai-embed-large` in the list.

### 4. Quick test

```bash
ollama run llama3.2:3b "Say hello in one sentence."
```

If you get a reply, the LLM side works. Exit the interactive prompt with `/bye`.

To test the embedding model through the API:

```bash
curl http://localhost:11434/api/embed \
  -d '{"model": "mxbai-embed-large", "input": "test sentence"}'
```

A JSON response containing an `embeddings` array means it works.

### 5. Useful Ollama commands

| Command | Purpose |
|---|---|
| `ollama list` | Show installed models |
| `ollama ps` | Show models currently loaded in memory |
| `ollama pull <model>` | Download or update a model |
| `ollama rm <model>` | Delete a model to free disk space |
| `ollama show <model>` | Display model details (size, parameters, context length) |
| `ollama serve` | Start the Ollama server manually |

### 6. Optional: Ollama on a different host or port

By default the LangChain Ollama classes connect to `http://localhost:11434`. If Ollama runs elsewhere (another machine, a Docker container, a custom port), you have two options.

Set the host for the Ollama server itself:

```bash
OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

And/or pass `base_url` explicitly in the code:

```python
embeddings = OllamaEmbeddings(model="mxbai-embed-large", base_url="http://my-server:11434")
model = OllamaLLM(model="llama3.2:3b", base_url="http://my-server:11434")
```

### 7. Choosing a different model

The answer model name is set by `model` in `settings.json`. If your hardware allows it, larger models usually give noticeably better answers:

| Model | Approx. size | Notes |
|---|---|---|
| `llama3.2:3b` | ~2 GB | Default; fast, runs on modest hardware |
| `llama3.1:8b` | ~4.7 GB | Better reasoning and instruction following |
| `mistral` | ~4 GB | Good general-purpose alternative |
| `qwen2.5:7b` | ~4.7 GB | Strong multilingual support, useful for German content |

Pull the model with `ollama pull <name>` and update `model` in `settings.json`. Restart the CLI or Streamlit server to load the change.

> **Important:** the embedding model is different. If you change `mxbai-embed-large` in `vertorize.py`, you must delete the existing database and re-index (see [Re-indexing](#re-indexing-your-documents)), because vectors from different embedding models are not compatible.

## Usage

You can use the RAG in two ways. Both options use the same study materials and RAG pipeline:

| Option | Interface | How to start |
|---|---|---|
| CLI | Ask questions and read answers in the terminal. | `python main.py` |
| Streamlit GUI | Ask questions in your browser and view formatted answers with LaTeX formulas. | Double-click `start_interface.bat` on Windows, or run `python -m streamlit run interface_handler.py` with your virtual environment activated. |

Keep Ollama running with both required models installed for either option.

### Option 1: CLI

With your virtual environment activated, start the command-line interface:

```bash
python main.py
```

**First run:** the database folder is missing or empty, so it loads every PDF, splits it, embeds all chunks and stores them in `./chroma_chapters`. Depending on the amount of material this can take from seconds to several minutes. You will see output like:

```
Checking for documents to index...
Loading: ./materials/optics_script.pdf
Loaded and split ./materials/optics_script.pdf into 148 chunks.
Indexed 16/148 new chunks.
...
Indexed 148/148 new chunks.
Documents added to database.

--- The Study Expert is ready to answer your questions ---

You:
```

**Later runs:** the database folder contains files, so all PDF processing is skipped, including any newly added PDFs:

```
Database folder is not empty: ./chroma_chapters. Skipping PDF processing.
```

**Asking questions:**

```
You: What is the difference between numerical aperture and magnification?

Study Expert: <answer based on the retrieved script excerpts>
```

If the retrieved excerpts do not contain the answer, the model is instructed to reply:

> There is no information about this in the original Study scripts.

**Leaving the app:** press **Ctrl+C**. The CLI currently checks `exit`/`quit` after appending the configured `text-extention`, so those commands only work when that extension is empty.

The browser interface displays your question and the RAG answer in two columns.
It uses the same model, prompt, and retriever as the CLI through `build_chain()`
in `main.py`.

Install Streamlit in your project virtual environment if needed:

```powershell
.\venv\Scripts\python.exe -m pip install streamlit
```

**Start on Windows:** double-click `start_interface.bat` in the project folder.
The launcher switches to the project directory and uses `venv\Scripts\python.exe`

Alternatively, run this from the project folder:

```powershell
.\venv\Scripts\python.exe -m streamlit run interface_handler.py
```

With your virtual environment activated, you can also use:

```bash
python -m streamlit run interface_handler.py
```

Open **http://localhost:8501** if your browser does not open automatically.
Use the Streamlit launch command above when starting the interface; running
`python interface_handler.py` directly produces `missing ScriptRunContext` warnings.

Keep Ollama running with `llama3.2:3b` and `mxbai-embed-large` installed.
Enter a question and click **Ask Study Expert**. A loading indicator appears while
the app retrieves relevant excerpts and generates an answer. The first question
can take longer while the database and models load. The pipeline is cached across
reruns, and the latest answer stays visible in your browser session. Empty
questions show a warning; generation failures show an error with expandable details.

**Formatted answers and LaTeX:** answers render as Markdown in a scrollable panel,
including lists, emphasis, and mathematical formulas. Supported math delimiters are:

| Formula style | Delimiters | Example |
|---|---|---|
| Inline | `$...$` or `\(...\)` | `$f = ma$` |
| Separate equation | `$$...$$` or `\[...\]` | `\[\frac{1}{f} = \frac{1}{g} + \frac{1}{b}\]` |

The interface converts LaTeX parentheses and brackets to Markdown math delimiters
while preserving inline code and fenced code blocks. The model must include math
delimiters in its response for formulas to render; plain text formulas remain text.

To stop the interface, press **Ctrl+C** in the terminal that launched it.

## Configuration Reference

The answer model and prompt profiles live in `settings.json`; ingestion and retrieval settings are constants in `vertorize.py`. Restart the app after changing configuration.

### `vertorize.py`

| Setting | Default | Meaning |
|---|---|---|
| `MATERIALS_FOLDER` | `"./materials"` | Folder scanned for `*.pdf` files |
| `DB_PATH` | `"./chroma_chapters"` | Directory where Chroma persists its data |
| Embedding model | `mxbai-embed-large` | Ollama model used to create vectors |
| Collection name | `study_materials` | Chroma collection holding the chunks |
| `CHUNK_SIZE` | `2500` | Maximum characters per chunk |
| `CHUNK_OVERLAP` | `250` | Characters shared between neighbouring chunks, to avoid cutting context at chunk borders |
| `ADD_START_INDEX` | `True` | Stores each chunk's start position in its metadata |
| `EMBEDDING_BATCH_SIZE` | `16` | Maximum chunks embedded per indexing batch |
| `search_kwargs={"k": 3}` | `3` | Number of chunks retrieved per question |

### `settings.json` and `main.py`

| Setting | Current value | Meaning |
|---|---|---|
| `model` | `llama3.2:3b` | Ollama model that writes answers |
| `PROMPT_TEMPLATE` in `main.py` | `scientific_beta` | Selects a profile under `prompt_type` |
| `prompt_type.<profile>.description` | see JSON | Instructions joined into the prompt, including grounding and citations |
| `prompt_type.<profile>.text-extention` | LaTeX instructions | Appended to the question before retrieval and generation |
| `prompt_type.<profile>.parameters` | `temperature: 0.7`, `max_tokens: 1500` | Currently stored only; these values are not passed to `OllamaLLM` |

### Tuning tips

- **Answers miss details:** increase `k` (e.g. 6–8) or reduce `chunk_size` (e.g. 1000–1500) for more precise matches.
- **Answers lack context:** increase `chunk_size` or `chunk_overlap`.
- **Slow responses:** lower `k`, or use a smaller model. More retrieved text means a longer prompt and slower generation.
- Changing chunking parameters requires [re-indexing](#re-indexing-your-documents).

## Code Walkthrough

### `vertorize.py` – ingestion and retrieval

1. **Decide whether to index.** Before opening Chroma, check whether `DB_PATH` contains files. Index PDFs only when the folder is missing or empty.
2. **Create embeddings and the vector store.** `OllamaEmbeddings` talks to Ollama; `Chroma` is opened with a persistent directory so data survives restarts.
3. **Load PDFs.** `glob` finds all PDFs in `materials/`; `PyPDFLoader` returns one `Document` per page, including page metadata.
4. **Split into chunks.** `RecursiveCharacterTextSplitter` splits on paragraphs, then lines, then words, to keep chunks semantically coherent.
5. **Store.** `vector_store.add_documents(...)` embeds chunks in batches of 16 and writes them to Chroma using stable SHA-256 chunk IDs.
6. **Expose a retriever.** `vector_store.as_retriever(search_kwargs={"k": 3})` returns the three most similar chunks for any query.

`pdf_metadata.py` reads numbered PDF bookmarks (such as `1 Introduction` and
`1.1 Background`) to assign chapters and sections. Page numbers are physical,
1-based PDF pages, which can differ from printed page numbers. Missing chapter
or section information appears as `Unknown Chapter` / `Unknown Section`.
Metadata is assigned per page: when multiple sections start on one page, the
last bookmark on that page applies to the entire page. To inspect this mapping,
run `python pdf_metadata.py`.

### `main.py` - the chat application

1. Loads `settings.json` and creates `OllamaLLM` with the configured model.
2. Selects the `scientific_beta` prompt profile via `PROMPT_TEMPLATE`.
3. Retrieves three chunks and formats their text and metadata with source labels.
4. Generates an answer and returns it together with the question and retrieved documents.
5. The CLI prints the answer, individual source details, and a summary grouped by PDF, chapter, and section, with unique retrieved pages sorted numerically.

## Re-indexing Your Documents

PDF processing is skipped whenever the database folder (`./chroma_chapters`, configured by `DB_PATH` in `vertorize.py`) is not empty. **To process a new PDF, stop the app and delete all files and subfolders inside the database folder so it is empty.** Then add the PDF to `materials/` and restart the app. All PDFs in `materials/` will be processed again.

The same rebuild is required after changing chunk settings, the embedding model, or metadata extraction logic. Existing databases do not gain new chapter/section metadata automatically. If indexing is interrupted, the partially populated database also causes later runs to skip ingestion; rebuild it to index all documents. Alternatively, delete the entire database folder before restarting:

```bash
# Linux / macOS
rm -rf chroma_chapters

# Windows (PowerShell)
Remove-Item -Recurse -Force chroma_chapters

python main.py
```
